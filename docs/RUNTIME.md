# 구동 안정성 시험 요약

Pleos 가이드의 안정성·리소스 항목을 에뮬레이터에서 직접 잰 결과입니다. 에뮬레이터 CPU는 실차 SoC와 다르므로 CPU 값은 상대 비교용입니다.

**환경**: AVD `Pleos_Connect_v2_1`(API 34, x86_64), 서명된 release APK, 기록 중 상태에서 시나리오 리플레이(`scripts/recap-scenario-*.json`)를 Console로 주입. 내비는 연결하지 않았습니다.

## 1.9.0 release 30분 연속 주행

시나리오 H(차선 변경·급제동·켜 둔 채 주행을 한 바퀴로 묶은 약 2분 시나리오) 16바퀴, 약 31분.

| 항목 | 결과 |
|---|---|
| 크래시·강제 종료 | 0회. 화면 프로세스와 기록 프로세스의 PID가 시험 내내 같음 |
| 메모리(PSS) | 화면 프로세스 35.7~39.1MB 사이를 오르내림, 기록 프로세스 22.8~26.8MB. 우상향 없음. 가이드 기준 400MB의 1/10 수준 |
| CPU | 32회 측정 중 0% 29회, 3.8% 2회, 7.6% 1회. 평균 약 0.5% (두 프로세스를 각각 잰 값, 에뮬레이터 코어 기준) |
| 화면 집계 | 주행 1,724초, 짚어볼 순간 80개(16바퀴 × 5), 모은 잘한 순간 16(바퀴마다 1) |

## 콜드 스타트

`am start -W`의 TotalTime 기준. 가이드 기준은 10초 이내입니다.

| 버전 | 측정값 |
|---|---|
| 1.5.2 release | 623 / 440 / 456ms |
| 1.6.0 release | 395ms, 아이콘 변경 뒤 재측정 698ms |
| 1.4.0 debug(참고) | 730ms |

## 상태 복원

복기 화면에서 홈이나 내비로 나갔다 돌아오거나, 백그라운드에서 프로세스를 강제 종료(`am kill`)한 뒤 다시 실행해도 복기 화면과 카드 스크롤 위치가 그대로 돌아옵니다. 기록 서비스는 화면 프로세스와 별개 프로세스라 계속 살아 있습니다. 이 측정은 카드 목록 화면이던 1.4.1 기준입니다. 1.8.0부터 복기는 한 장씩 보는 화면이며, 1.9.2부터는 화면 프로세스가 종료된 뒤에도 보던 카드로 돌아옵니다(아래 1.9.2 절).

## 그 밖에 확인한 것

- 오늘 복기 화면 전환(1.4.1): 카드 120개에서 149~190ms.
- 프레임: 버튼 조작과 스크롤 341프레임에서 p50 8ms, p99 19ms.
- 자정을 넘기는 주행은 넘긴 뒤의 카드가 다음 날 복기로 들어갑니다.
- 업데이트 설치: 1.8.0 위에 1.9.0 release를 `adb install -r`로 덮어 설치해 성공했고 크래시는 없었습니다.

## 1.9.1

1.9.1은 쓰지 않는 차량 권한과 진단 메뉴를 release에서 뺀 정리 릴리스입니다. 판정 로직과 화면은 같습니다. 제출 APK로 30분 시험과 콜드 스타트를 위와 같은 방법으로 다시 쟀습니다(2026-11-02). release에는 모의 내비 수신기가 없어, 시나리오 H의 차량 신호만 Console로 넣는 개발용 재생 도구(저장소 밖)로 돌렸습니다.

| 항목 | 1.9.0 | 1.9.1 |
|---|---|---|
| 주행 | 16바퀴, 약 31분 | 16바퀴, 32분 35초 |
| 크래시·강제 종료 | 0회, PID 동일 | 0회, 두 프로세스 PID 동일 |
| 메모리(PSS) | 화면 35.7~39.1MB, 기록 22.8~26.8MB | 화면 28.3~31.1MB, 기록 19.5~23.2MB. 바퀴당 +0.1MB 이하로 증가 추세 없음 |
| CPU(16회 × 두 프로세스 = 32회) | 0% 29회, 3.8% 2회, 7.6% 1회, 평균 0.48% | 0% 25회, 3.8% 7회, 평균 0.83% |
| 화면 집계 | 주행 1,724초, 짚어볼 순간 80, 잘한 순간 16 | 주행 1,718초, 짚어볼 순간 80, 잘한 순간 16 |
| 콜드 스타트 | (1.6.0) 395~698ms | 548 / 642 / 544ms |

CPU는 `top` 한 번 샘플의 해상도가 3.8% 단위라, 평균 차이는 3.8%가 몇 번 잡혔는지(2회와 7회)의 차이입니다. 32회 표본으로는 두 버전의 차이를 말할 수 없고, 둘 다 가이드 기준 5%보다 훨씬 낮습니다. 1.9.1은 판정 로직이 바뀌지 않아 CPU가 실제로 늘었다고 볼 근거는 없습니다.

같은 날 저장소를 새로 받아 README 순서대로 앱 삭제 → 설치 → 권한 허용 → 기록 → 시나리오 D 재생을 따라 했고, 복기 결과(잘한 순간 1·놓친 순간 1·늦게 켬 1·급제동 1, 카드 4·애매함 0)가 README 기대값과 같았습니다.

## 1.9.2

1.9.2는 AI 보조 기본값을 꺼짐으로 바꾸고, 보던 카드를 저장해 프로세스 종료 뒤에도 복원하도록 한 릴리스입니다. 판정 로직과 화면 문구는 1.9.1과 같아 30분 시험은 1.9.1 결과를 씁니다. 같은 날(2026-11-02) 제출 APK로 다음을 확인했습니다.

| 항목 | 결과 |
|---|---|
| 단위·재생 시험 | 443개 중 439개 통과, 4개 건너뜀, 실패 0 |
| 첫 실행 | 앱 삭제 후 설치, 홈 타일 `AI 보조 · 꺼짐` |
| 시나리오 D | 카드 4장(잘한 순간 1·놓친 순간 1·늦게 켬 1·급제동 1), 애매함 0, 기본 문구 |
| 프로세스 종료 뒤 복원 | 복기에서 3번째 카드를 연 채 앱을 멈추고 `am kill`로 화면 프로세스를 종료(PID 바뀜)한 뒤 다시 열어 3/4 카드로 돌아옴 |
| 콜드 스타트 | 469 / 496 / 498ms |

1.9.1·1.9.2의 시나리오 D 결과는 1.9.3에서 시나리오를 바꾸기 전 파일로 잰 값입니다.

## 1.9.3 시나리오 D

1.9.3은 시나리오 D에 깜빡이를 켠 채 순항하는 구간을 넣고 첫 차선 변경의 조향 부호를 바꿨습니다. 처음 파일로 2026-11-03 제출 APK를 4번 재생했을 때는 깜빡이 없이 바꾸는 두 번째 차선 변경이 한 번도 놓친 순간 카드가 되지 않았고(4장 3회, 3장 1회), 한 번은 잘한 순간도 빠졌습니다.

원인은 조향 부호나 속도 신호가 아니었습니다. debug 빌드로 같은 파일을 재생해 보니 속도 알림은 약 0.15초마다 계속 왔고, 앱이 받은 입력을 그대로 로직에 다시 넣으면 같은 결과(놓친 순간 없음)가 나왔습니다. 두 번째 차선 변경은 지연 창이 추정한 측면 이동이 1.6~2.0m로, 차선 변경으로 보는 하한(2.0~2.5m)에 못 미쳤습니다. Console HTTP 쓰기가 밀리면서 0.35초 간격으로 보낸 조향 단계가 앱에는 0.18~0.52초 간격으로 들어왔고, 폭이 작은 차선 변경이 경계 아래로 떨어진 것입니다. 첫 번째 차선 변경의 부호를 되돌려도 결과는 같았습니다.

그래서 앱 코드는 그대로 두고 시나리오만 고쳤습니다. 세 차선 변경의 조향 폭을 키우고(첫 번째 최대 22도, 세 번째 20도), 두 번째는 0.45초 간격 3.15초로 늘렸습니다. 왼쪽 차선 변경의 첫 조향이 음수인 방향 의미와 시각(10초·17초·24초 시작, 전체 94초)은 그대로입니다. 고친 파일을 같은 APK(설치본 SHA-256 `d630ecb0…a29acc31` 일치, `-no-audio` 에뮬레이터)로, 회차마다 앱 데이터를 지우고 6번 재생했습니다.

| 회차 | 복기 카드 |
|---|---|
| 1~6 | 5장: 잘한 순간 1·놓친 순간 1·늦게 켬 1·켜 둔 채 1·급제동 1, 애매함 0, 기본 문구 |

급제동 카드의 시작·끝 속도는 감속이 가장 큰 0.4~2초 구간이라 회차마다 다릅니다(예: 42→27 km/h, 8.6 m/s²). 명령한 감속은 60→15 km/h(8.33 m/s²)입니다.

## 한계

- 에뮬레이터 측정이며 실차 SoC·실주행 신호에서의 값이 아닙니다.
- 실제 NaviHelper 안내 수신(TBT)은 에뮬레이터의 GNSS 제약으로 확인하지 못했습니다. 내비가 없으면 기존 규칙 판정으로 동작합니다.
